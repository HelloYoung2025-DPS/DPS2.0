# Binding operations

The module remains proposed. `identity_binding_v1` enables writes and `kill_identity_binding_writes` stops all new bind/revoke mutations. Production composition uses `PostgresBindingRegistry.CreateForCompositionAsync` with the public contract clients returned by each provider-owned factory and a short-lived `binding.composition.attestation/v1`. The verifier has one pinned P-256 root public key and binds the signed Release BOM digest, monotonically assigned generation, UTC validity window, exact implementation and contract-pack SHA-256 values for binding and both providers, the composition-host artifact, and each non-secret instance-configuration digest and trust epoch. It additionally requires the exact non-public sealed implementation type and assembly identities compiled into binding policy. A caller-generated key, alternate implementation type, public or unsealed implementation, expired attestation, wrong database target, wrong trust epoch, or digest mismatch is rejected before provider recovery or registry use. Binding source has no project reference or friend-assembly access to provider source. Request-derived proof DTOs, model output, cached caller claims, arbitrary production dependency injection, and direct cross-module SQL are forbidden.

The corresponding root private key is deliberately absent from this repository. The current pinned public key is a fail-closed bootstrap anchor; the module remains `releaseEligible: false` until an independently controlled signer can issue a Release BOM attestation, a trusted host verifies the Release BOM before loading any in-process assembly, and the root-rotation/revocation procedure has raw evidence. Hashing `Assembly.Location` after load cannot itself prove which bytes were mapped into memory, so the host pre-load check is an explicit release blocker rather than an overstated guarantee. Tests may use the internal test-only constructor and internal verifier overload, but neither route is public production composition.

The production factory verifies the attestation, applies the ordered idempotent module migrations, verifies the still-current attestation again, then records the highest accepted generation under a PostgreSQL advisory lock before recovering pending attempts. A lower generation or a different descriptor for the same generation fails closed across process restarts. Normal startup therefore has no migration/generation bootstrap cycle; an independently approved database role and migration review are still required.

Bind is a durable saga. A module-owned pending attempt first records the exact device and account revisions and deterministic reservation ID. Each provider then reserves and confirms that exact revision under its own resource lock. Only after both confirmations does binding atomically commit its current row, append-only revision, idempotency receipt, outbox event, and committed-attempt state. Same-request retry resumes pending work after a process crash; a partial provider failure is compensated under the binding idempotency lock. An active reservation makes provider retirement, capability changes, suspension, revocation, and authorization refresh fail closed until binding revocation commits and releases both reservations.

Conflicting idempotency keys store only a scoped digest in quarantine and are rejected. Partial unique indexes enforce one active binding per device and platform account, while a trigger prevents revision update/delete. A returned old bind receipt is rejected after revocation instead of returning historical active truth. If provider release fails after the local revoke commit, the revoke call fails; retrying the exact revoke receipt retries release without rewriting binding history.

`identity.binding.mutation.fence/v1` closes consumer commit-time revocation races. `CreateMutationFenceClient` returns the contracts-only client used by controlled composition. Acquire takes only the exact Soul/binding/account scope and operation envelope; it does not accept a caller-supplied binding proof or revision. Binding resolves the current active revision while holding the same PostgreSQL session advisory-lock key used by revoke. The consumer keeps the returned async-disposable lease through commit or rollback, then disposes it. Revoke cannot pass the lock while the lease is held. The fence always uses a dedicated non-pooled PostgreSQL connection. Release is idempotent, bounded to five seconds, and non-throwing after the consumer commit; explicit unlock is attempted for audit quality, while physical connection close is authoritative. A null `released_at` therefore means abnormal cleanup evidence, not proof that the advisory lock remains held.

Shadow comparisons precede any human-approved bounded canary. Rollback stops new writes and has the independent Release Controller issue a higher composition generation that selects the previous stable BOM; replaying the previous attestation generation is forbidden. Rollback never deletes binding attempts, bindings, append-only revisions, receipts, quarantine, provider reservations, or outbox rows. A database restore must also rotate the instance trust epoch and receive a new higher-generation attestation so backup restoration cannot reopen an old signed generation. Keep the expand-only schema until the previous BOM demonstrates read compatibility. Never point Integration tests at port 55434 or the `dps_gbrain_company` database.
