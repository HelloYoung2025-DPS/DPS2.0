# Binding migrations

`001_create_binding.sql` creates module-owned pending binding attempts, current bindings with their provider reservation ID, append-only revisions, idempotency receipts, scoped conflict quarantine, and a canonical-text transactional outbox. `002_upgrade_binding_saga.sql` is an idempotent pre-release convergence migration: it rejects old rows that have no authentic provider reservation or authoritative quarantine scope instead of fabricating them. No 0.1/0.2 database was release-eligible. `003_add_mutation_fences.sql` adds audit rows for commit-spanning binding mutation fences. `004_add_composition_generation_fence.sql` stores the highest accepted signed Release BOM generation and immutable descriptor so process restart cannot reopen an older generation. `005_harden_canonical_identifiers.sql` adds fail-closed database constraints for the repository-wide `db_`/`pa_`/`trace_` 32-hex and `idem_` 64-hex formats, including convergence of already-created proposed schemas. Partial unique indexes enforce one active binding per device and platform account; a database trigger rejects revision update/delete.

Deployment order is strict: apply all device-registry migrations in lexical order, then all platform-account-registry migrations in lexical order, then all binding migrations in lexical order. The production async factory verifies its signed composition before applying binding migrations, records each embedded migration ID and SHA-256 in `module_schema_migrations`, rejects an edited applied migration, verifies the still-current composition again, and then records the generation fence. Binding never joins provider schemas; the order only ensures both provider reservation APIs exist before the binding saga is enabled. Rollback disables binding and fence acquisition first, drains or recovers pending attempts and consumer fences, and only then rolls back provider routing. The expand-only schemas remain in place throughout the N/N-1 window; a normal rollback uses a newly signed higher generation and never lowers the recorded highest generation.

Future changes use expand-migrate-contract migrations. Consumers use versioned contracts or exact scoped queries and never read these tables. Never join to device-registry or platform-account-registry schemas.
