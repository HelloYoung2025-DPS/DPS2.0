# Test boundaries

- `unit`: leases, request hashes, idempotency, allowlists, and native/postcondition truth.
- `contract`: the audited fixed .NET wrapper uses floor `1`; the central candidate policy injects the higher count for strict wire validation, versioned duplicate/retry truth, and owner-defined golden vectors.
- `provider-contracts`: a required Python consumer-differential suite reads the Supervisor, Journal, and Executor owner Schemas, locks the exact 55-case Supervisor/Journal provider-owned corpus ID sets (including the signed Supervisor directive and Worker-only durable-drain receipt), binds both drain auth profiles and the owner checksum machine profile, and treats the Executor-owned `native.stop.proof/v1` vectors only as bounded quarantine classifiers. The worker keeps no private copy of those Schemas or profiles; an owner case or profile change forces explicit consumer rebinding.
- `Integration`: the audited fixed wrapper likewise keeps floor `1`, while the central policy injects the higher simulation count for crash phases, persistent retry budgets, Journal append failure, crash-after-append reconciliation, persistent drain truth, exact Worker receipt PREPARED/COMMITTED recovery, PSS retry idempotency, signed-directive continuation, clock rollback, real local-process termination/restart, exclusive writer fencing, filesystem permissions and effective-user ownership, handle/path identity, symbolic/hard-link and FIFO rejection, bounded crash-tail recovery, tamper, hard resource limits, and legacy v1 quarantine. The latter proves repeated, concurrent, cancelled, and conflicting v1 requests cause zero runtime-identity reads, zero native-stop calls, zero signature operations, and zero proof files; restart exposes only bounded owner-decoded metadata. These tests keep `EvidenceKind=SIMULATION`; process-boundary cases also carry `ExecutionBoundary=LOCAL_PROCESS`.

The terminal-audit simulations assert that a terminal receipt is not returned while its deterministic Journal append is missing, that a repeated request reuses the same `entry_id` and payload hash after an append failure, and that startup reconciliation finishes a crash-after-append record without redispatch or command redelivery. The Journal test adapter independently canonicalizes and hashes the payload instead of echoing the worker's claimed hash, and a cross-module simulation sends the worker DTO through the real owner `JournalStore`; corrupted and raw-noncanonical hashes fail. A separate executable process harness runs the real `CommandProcessor.ProcessAsync` decision path and terminates at four durable boundaries: transport invoked before a side effect, native side effect before acknowledgement, dispatch acknowledgement persisted, and terminal Journal append before final state. The reconcile-only host is then restarted to prove exact completion replay or persistent uncertain blocking without incrementing the native side-effect counter. Production-composition tests also assert that simulation adapters are rejected in `WorkerRuntimeMode.Production`.

Drain-receipt simulations use distinct ephemeral Supervisor and Worker keys. They prove invalid, stale, wrong-scope, wrong-key, and bad-signature directives cannot stop intake; a long drain gets a fresh completion window; non-UTC time and rollback fail closed; exact raw Worker wire is persisted before append; a crash after the real owner Journal durable append reuses the same wire and signature; same signed statement with a newly randomized Supervisor PSS signature is idempotent; changed routing epoch quarantines; and the returned Worker wire has no Journal-owned rich proof fields. The Journal implementation is wrapped test-only behind append plus readiness, so these remain simulation rather than production IPC or Windows evidence.

Legacy-native-stop tests inject counting collaborators solely to prove none are invoked. They do not issue or durably reuse a proof. A local-process launch test also exercises the real Worker entry point with the Supervisor's current zero-argument launch shape and requires exit `64`, usage-only stderr, no stdout status, no runtime-state creation, and therefore no Worker intake or route transition. This is negative compatibility evidence only; it does not simulate a successful stage, health check, cutover, or Windows host. The Policy v2/challenge, Release-BOM authority, Supervisor route assignment, authenticated live Worker IPC, shared fixed launch ABI, Windows ABI, and production key service remain `WAITING_EXTERNAL`.

These tests do not invoke ZennoDroid or a phone. They are labelled unit, contract, or `SIMULATION` and cannot issue Windows or device verification.
