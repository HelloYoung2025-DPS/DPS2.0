# Control Plane Host migrations

`001_create_control_plane_truth.sql` establishes the module-owned PostgreSQL 18.4 runtime-truth boundary. Apply it only through `PostgresControlPlaneTruthMigrator` with a privileged migration DSN, a dedicated Control Plane database, and an already-created independent runtime login role. The migration revokes database `TEMP`/`CREATE` from public/runtime, and the runtime role receives only schema usage, `SELECT` on provider trust, runtime truth, receipts, quarantine and outbox, plus execution of the exact JSON helper and two fixed atomic write functions. It never receives direct table `INSERT`.

All five tables have update/delete and truncate triggers. Bootstrap creates a new schema exclusively and refuses every unmarked pre-existing schema; a concurrent creator causes rollback rather than adoption. PostgreSQL 18.4 supplies each named constraint's exact `pg_get_constraintdef` baseline, which is stored in its migration comment and never re-baselined on later runs. Runtime startup attests its exact session/current identity, timeout and trigger mode, a bidirectionally isolated `NOINHERIT` role graph, persistent non-RLS relation shape, all columns against the built-in `pg_catalog."C"` collation, exact constraint baselines, independent indexes, object ACLs, migration ownership, function body hashes/security modes, and all 13 trigger tuples before each operation. The migration owner remains a trusted boundary: a compromised owner can alter both an object and its baseline comment, so these checks prove runtime/accidental drift resistance, not owner compromise resistance. New migrations use expand-migrate-contract and must preserve the prior signed BOM's read compatibility. Never target port 55434 or the `dps_gbrain_company` database.

`002_create_release_binding_truth.sql` establishes the separate durable Active Release Binding boundary. Apply it only through `PostgresReleaseBindingTruthMigrator` with the same exact PostgreSQL 18.4, dedicated database, timeout, and distinct migration/runtime-login requirements as migration 001. It owns exactly two append-only tables:

- `release_binding_journal` stores one exactly-next sequence per `device_binding_id`, the exact `release.binding.receipt/v1`, current and previous `active.release.binding/v1` wires, request digest, signer ordinal, and the applicable canonical Release BOM bytes. Every non-bootstrap activation additionally stores the exact externally signed previous `STABLE` lifecycle-twin wire; bootstrap activation, revocation, and rollback must not carry it.
- `release_binding_recovery_fences` stores the idempotent recovery ID, exact journal head, BOM digest/generation, and recovery-content digest. A fence can commit only while that same head remains active.

The runtime has `SELECT` on only those two tables and `EXECUTE` on only two fixed `SECURITY DEFINER` functions. `append_release_binding_record` takes the per-device advisory transaction lock, checks the receipt/binding identity and exactly-next sequence, and atomically appends the journal row. `commit_release_binding_recovery_fence` takes the same lock, permits exact redelivery of a committed fence, rechecks the active journal head, and atomically appends the fence. Runtime receives no direct `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, DDL, role inheritance, database `TEMP`, or migration authority; row and truncate triggers independently reject mutation.

Each exact canonical SIGNED or STABLE Release BOM wire is bounded to 4 MiB. The migration is deliberately rerunnable on its marked R0-C schema: it replaces the earlier signed-BOM size constraint and adds/replaces the exact previous-STABLE shape and size constraints. Existing rows that cannot prove the current invariant make the migration fail rather than being grandfathered. Before opening a runtime store connection, the implementation verifies the exact runtime session identity and schema marker, an inventory of exactly these two relations, migration-role table ownership, runtime `SELECT` with every direct mutation privilege absent, both append-only trigger pairs, and exactly two migration-owned `SECURITY DEFINER` functions with `search_path=pg_catalog`.
