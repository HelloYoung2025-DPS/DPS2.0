# Control Plane Host operations

## Active Release Binding

Control Plane Host owns the durable `active.release.binding/v1` truth and `release.binding.receipt/v1` transition history, keyed by exact `device_binding_id`. Activation accepts one exact canonical externally signed `SIGNED` candidate, the signer-committed opaque 256-bit execution token, and—except at bootstrap—the exact externally signed `STABLE` lifecycle twin of the current SIGNED binding. It verifies both RSA-PSS signatures, the token commitment, the candidate's previous-stable ID/digest, and deep lifecycle identity before appending. Control Plane Host never creates a Release BOM, converts SIGNED to STABLE, or receives a release-signing private key.

Runtime `generation` is strictly monotonic per device and advances on activation and rollback. The separate signer `release_bom_generation` must increase on every new activation but may revert when rollback restores the exact retained previous BOM. Revocation preserves digest and runtime generation, changes only the active state to `revoked`, and does not mint a replacement token. Rollback requires the previous binding's signer-committed token, re-verifies its exact retained signed BOM, advances runtime generation, and consumes the previous slot. Activation, revocation, and rollback each append one strict versioned receipt before publishing in-memory state. After acquiring the per-device transition scope, every mutation first replays the durable head through the same full recovery validator; therefore an exact retry after a commit acknowledgement loss or from a stale authority returns the original committed receipt only while its device, request kind, and postcondition remain exact. A request whose committed postcondition was later superseded is consumed and fails closed rather than becoming a fresh transition; a different request also fails closed when it conflicts with current truth.

The only supported consumer composition starts from the sealed `ActiveReleaseBindingRecoveryCapability` issued by that authority over its exact PostgreSQL store. `PolicyBoundReleaseBomFactsSource` and executor-gateway's `ControlPlaneHostActiveReleaseBomReader` both require that durable capability; neither accepts a public implementable production reader, a per-consumer store, or an independent cache as authority. Policy receives the active digest and the same runtime generation through the Control-host-owned source, avoiding a reverse module dependency, while executor receives that digest, generation, and the same opaque token. Reads consult the durable per-device journal head and replay validated deltas before serving; missing, revoked, stale, foreign-device, unreachable, or unverifiable state fails closed.

Activation, revocation, rollback, and Policy recovery share one durable per-device serialization primitive. The PostgreSQL store acquires the device advisory transaction lock before the authority gate, commits the exactly-next journal row before publication, and holds the same lock across a Policy recovery lease and commit. The host has no production listener and `--self-check` does not install a production composition root; bounded production wiring, human approval, kill switch, and rollback remain required. The required same-instance PostgreSQL gate proves both consumer paths observe the same running authority/store across activation, revocation, rollback, and restart.

## Submission lifecycle

Policy Approval uniquely owns the strict reconciliation, recovery, and signed submission-state contracts. Control Plane Host uses only that public contract pack. Reconciliation and human recovery signing are separate, strongly typed asynchronous external capabilities with different canonical P-256 identities; the recovery authority receives the complete bounded recovery DTO before it can authorize a signature, and the host never accepts raw lifecycle private-key material. Authority calls and Policy port calls each have a hard maximum five-second timeout and recheck cancellation before and after every external boundary. A timed-out or indeterminately cancelled authority is quarantined: no second call may start, its private payload copy remains intact until the uncooperative task finishes, and any late signature plus payload are then zeroed without emitting a wire. This is fail-closed containment, not proof that a remote authority stopped processing; a production authority must use an abortable authenticated process boundary and idempotent approval receipt.

The current `in-process-api` ports are proposed role-specific contract facades only. Distinct objects, exact auth-scope declarations, different credential-authority fingerprints, and bounded calls are local fail-closed configuration checks; they are not evidence of peer authentication, process isolation, credential isolation, or production composition. Production must replace these facades with authenticated role-specific IPC/RPC adapters whose independent credentials remain outside the Control host; those adapters must derive peer identity and authorization from the actual mTLS, OS-protected IPC, or equivalent Policy/database-role session rather than trusting the interface's self-reported strings. A Policy-state response is accepted only after strict codec, commitment, signature, exact identity/scope/idempotency, Release BOM, intent/native binding, predecessor, and evidence verification. Unknown, empty, timed-out, forged, or mismatched responses leave the old attempt blocked.

No production lifecycle composition is installed by `--self-check`. Activation remains R3, human-approved, exact-BOM-bound, and fail-closed until the independent reconciler, human approval broker with auditable approval receipts, Policy-state trust key, authenticated role-specific Policy IPC/RPC adapters, real PostgreSQL 18.4 integration, canary, kill switch, and rollback evidence exist. Rollback stops new lifecycle issuance; it never reopens or rewrites an old attempt.

The host is proposed and has no production listener. `--self-check` is the only accepted local startup mode. PostgreSQL migrations require an explicit non-runtime migration login and a dedicated Control Plane database target. Runtime uses a distinct, login-capable, non-member role. In the runtime-truth schema it has schema usage, `SELECT` only on the five truth tables, and `EXECUTE` only on the exact JSON helper plus the two fixed commit/quarantine functions. In the release-binding schema it has schema usage, `SELECT` only on the journal and recovery-fence tables, and `EXECUTE` only on the two fixed atomic functions described above. Runtime has no direct table `INSERT`, mutation, DDL, database `TEMP`, role inheritance, or migration role. Both paths enforce five-second connection, command, statement, lock, and idle-transaction limits, exact PostgreSQL 18.4, origin trigger execution, and rejection of GBrain Company's port/database.

`policy-approval` uniquely owns the strict `action.execution.promotion/v1` input contract; this module consumes its public contract pack and is the only allowed wire producer. A shadow proposal never authorizes execution. Production promotion issuance is not implemented in this slice: it remains fail-closed until an independently verified release-approval source and secret-backed P-256 signer are implemented, tested, and human-approved. The policy-owned codec fixes the exact bounded wire and canonical signature bytes so neither side can accept a loose substitute.

Every new or equivocal ingest starts from bounded strict UTF-8 raw v1 JSON bytes. The host rejects duplicate/additional fields and non-canonical identifiers, resolves the latest provider trust revision, requires its active release BOM and canonical NIST P-256 key, verifies the P1363 signature, and stores the exact raw bytes, digest, trust revision, public-key digest, signature, and authorization digest. An exact immutable redelivery whose raw bytes, BOM, key ID, signature, authorization digest, and committed record all match returns the existing receipt even after later key revocation; it creates no new truth, receipt, outbox, or quarantine row. One owner-controlled database function commits truth, receipt, and outbox in a single transaction; a second function appends only hash-scoped conflict quarantine. Startup attests the exact five-table/83-column/89-constraint catalog and persisted PG18.4 definition comments, 13 trigger tuples, three independent indexes, eight function bodies and security modes, isolated role graph, built-in `pg_catalog."C"` collation, object ownership, and ACLs before every operation.

For `soul.memory.readback/v1`, this host verifies the signed SoulMemory adapter proof and exact equality of its declared projection and read-back checksums. The source contract does not carry the original GBrain content, so the host does not claim that it locally recomputes a checksum from GBrain bytes.

Shadow truth comparison must precede a human-approved bounded canary. The kill switch stops ingest; rollback retains runtime truth, receipts, quarantine, and outbox rows and restores the previous signed BOM. Rollback never rewrites or truncates the journal.

Personal-data export, correction, retention enforcement, and verified erasure are not implemented in this slice. The append-only tables retain canonical scope identifiers and exact signed provider JSON bytes; this module therefore remains `releaseEligible: false` until an independently approved retention and cryptographic-erasure or equivalent audited design is executable and tested.
