# Command Orchestrator operations

Stop new leases with `kill_command_orchestrator`, drain known in-flight work, and quarantine any dispatched command without a verified receipt. Pre-dispatch expiration may requeue; post-dispatch expiration and `UNKNOWN_OUTCOME` require reconciliation. Command Orchestrator remains the producer and owner of `execution.authorization/v1`: it constructs the exact envelope from the database lease, calls only the versioned Policy Approval signing port, requires the declared Policy module and key fingerprint, rejects any payload mutation, and locally verifies the returned P-256 P1363 signature before relay. Bind the exact expected active-BOM generation and execution-token digest, but never treat those signed claims as current activation truth or expose the raw token. Rollback changes routing for future commands and never pretends an external side effect was undone.

The durable store requires exact PostgreSQL 18.4 and separate restricted `LOGIN NOINHERIT` migrator/runtime credentials targeting the same dedicated database. Neither role may have elevated attributes, memberships, per-role settings, or unexpected grants. The runtime role must use only the signed migration's `api_*` functions. Every API call also requires the command-orchestrator process's independent 256-bit capability; the migration ledger stores only its SHA-256, and the capability must never enter Git, logs, evidence, or a database connection string. Possession of the runtime database credential alone is insufficient to advance dispatch or receipt state. Rotate the capability only through a separately reviewed migration and coordinated process rollout.

Lease reservation, binding, dispatch-window validation, and expiry recovery take their authoritative timestamp from PostgreSQL `clock_timestamp()` only after the per-command advisory lock is held. Callers provide duration but never an absolute lease or recovery clock. Startup attestation requires the exact table, index, trigger, function, sequence, identity/owned-by and ACL inventories; any third-party object/default grant or sequence-parameter drift fails closed before runtime use.

Dispatch additionally requires an `execution.authorization/v1` signature that verifies against the configured independent Policy Approval NIST P-256 public trust root. Format validation, a propagated approval digest, or database access cannot substitute for signature verification. Startup is a hard gate: migration checksum, capability digest, catalog digest, role identity, API inventory, ACLs, function security settings, and append-only triggers must all attest before the service accepts work.

For recovery, run expired-lease reconciliation before issuing new leases. An expired pre-dispatch lease appends a recovery event and may receive the next bounded attempt. An expired post-dispatch lease is `ReconciliationRequired`; accept only an authentic receipt bound to its exact command, lease, attempt, authorization, and BOM fence. Never delete or edit command history to force progress. Roll back by stopping new leases and routing future commands to the previous signed BOM; preserve the database for audit and reconciliation.
