# Planner tests

The required Unit suite contains exactly 13 cases: 12 deterministic shadow-only behavior cases plus one machine-readable Integration inventory/classification check. The required C# Contract suite contains exactly 7 cases, and the required Python Contract Schema suite contains exactly 6 Draft 2020-12 cases. C# and Schema consume the same v2 adversarial corpus for action conditions, fixed typed digest references, missing/extra fields, prompt tokens without spaces, Unicode/confusables, PII, and hostile input. They also bind `action-proposal-major-modes.v1.json` to the central Manifest semantics: v1 is `quarantine-only` and cannot be produced or promoted, v2 is `active`, and neither major carries authority by itself.

The required Integration suite contains exactly 7 cases named in `required-real-local-process-tests.v1.json`, and every one starts at least one independent child process. It launches an explicit xUnit child-process fixture with the same pinned runtime, transfers bytes through isolated file IPC, and invokes the production `ShadowActionPlanner` plus the production `ActionProposalV2Json` codec. It covers byte-identical fresh-process replay, forced process death after planning but before proposal publication, strict malformed/duplicate/invalid-UTF-8/oversized wire rejection, typed-reference prompt/Unicode/PII attacks, shadow-only side-effect proposals, cross-Soul/device/account isolation, proposal scope/derived-identity/non-shadow authority tampering, explicit v1 rejection at the current production boundary, and unknown fixture/public-contract majors and actions. The endpoint is explicit and excluded from ordinary test discovery; the separate Unit inventory test cannot satisfy the Integration floor.

Crash-window readiness is written to a same-directory temporary file, flushed through the file handle, and atomically renamed. The parent reads the final file through one stable handle with bounded retry for visibility or sharing delays, verifies its exact schema and proposal digest, binds the child-reported PID to the already-held `Process` handle, confirms the child is still alive before kill, and confirms that exact PID exits non-zero before restart. Deadline and dispose cleanup also fail unless `WaitForExit(5000)` proves the killed child process exited.

This is `REAL_LOCAL_PROCESS` evidence for a pure proposal boundary, not a mock planner. It does not prove Policy Approval integration and does not authorize, compile, lease, execute, retry, or record an action. It also does not satisfy PostgreSQL, GBrain, network, Windows, ZennoDroid, ADB, device, canary, or scale evidence.
