# Policy Approval migrations

`001_create_policy_approval.sql` creates the PostgreSQL 18.4 append-only runtime-state, rate-consumption, decision, status-revision, idempotency-receipt, outbox, and hash-only quarantine tables. Runtime-state inserts and approval evaluation use the same scope advisory lock, closing the policy-revision race while a decision transaction is in flight. Rate consumption is a same-transaction append-only fact bound to the exact runtime revision; the trusted reader subtracts committed facts before a decision. `002_configure_policy_runtime_role.sql` grants the runtime role only the reads and inserts required by the production slice. The migrator uses a separate privileged connection and validates both the schema and role as lowercase allowlisted identifiers.

`003_create_submission_lifecycle.sql` adds append-only submission attempts, acknowledgements, uncertainty quarantines, independent reconciliations, and human recovery authorizations. `begin_approval_submission` commits the exact signed `SUBMISSION_PENDING` fact before native execution. Pending is thereafter treated as unknown until a durable exact acknowledgement is appended. Exact duplicate begin is readback-only; it never returns native-submit authority. Recovery requires both a signed `CONFIRMED_NOT_SUBMITTED` reconciliation and a separately signed next-attempt authorization, and it binds the exact same approval/proposal/command/Soul/device/account/trace/idempotency chain to a fresh attempt/lease/request rather than reopening the old row.

`004_create_native_stop_challenge_ledger.sql` additively defines proposed append-only issue/consume rows plus fenced, replay-safe functions intended to atomically consume one challenge into ACK or UNKNOWN. Static tests cover both tables' UPDATE/DELETE/TRUNCATE triggers and all three function REVOKEs. A required real PostgreSQL 18.4 suite inspects catalog/ACL state and proves actual role and owner mutation rejection; without that raw run the migration remains unverified. It grants those tables and functions to **no runtime role**, so the partial path is unreachable. A separately reviewed activation migration may grant the exact executor role only after the owner-defined signed contract artifact, sealed two-phase request commitment, fixed external trust, process guardian, and real crash/duplicate/race tests pass. The public runtime therefore remains `WAITING_EXTERNAL` before PENDING.

The generic runtime role receives no lifecycle access. Three pairwise-distinct login roles split persistence authority: executor gets begin/ack/quarantine, independent reconciler gets reconcile, and human recovery gets recover. They share read-only lifecycle facts but receive no direct mutation, helper execution, role membership, object ownership, or schema/DDL privilege. Each entrypoint validates an exact JSON field set, rechecks its exact login role, takes scope/approval/command/attempt advisory locks plus the attempt-row lock, re-reads PostgreSQL time after waiting, and refuses stale approval status, runtime revision, Release BOM generation, conflicting terminal state, or inconsistent predecessor.

Migration replay first drops the obsolete five-argument begin function and old generic-role helper. Runtime privilege guards enumerate all lifecycle function overloads, so an unknown or retained overload fails the process before use.

All durable tables reject `UPDATE`, `DELETE`, and `TRUNCATE`, including when the table owner issues the statement. Policy changes, revocations, submission states, reconciliations, and recoveries are represented as new immutable facts. Runtime migrations refuse the dedicated GBrain Company database and port `55434`.
