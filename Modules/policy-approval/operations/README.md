# Policy Approval operations

## 0.6.0 native dispatch status

Native dispatch is `WAITING_EXTERNAL`. Public production composition has no native callback or caller-selected trust provider. `SubmitNativeOnceAsync` verifies that the lease has not already produced a PENDING fact and then fails before any database mutation. Activation requires the exact signed Executor Gateway owner artifact plus a sealed two-phase commitment of the submitted request before first native byte. Operators must treat this as zero promotion, not degraded operation.

Policy Approval contains and packages no `native.stop.*` DTO, Schema, Corpus, codec, or verifier. Executor Gateway remains the unique registered owner. Do not route a native-stop artifact into Policy until a future Manifest dependency, compatibility edge, signed BOM binding, and activation review name its exact owner digest. Missing Release BOM authority, Supervisor route, Worker authority, currentness/revocation proof, or exact request binding is a hard stop. ACK never means action success: without exact business postcondition proof the result is `UNKNOWN_OUTCOME` and retry is forbidden.

Keep `kill_policy_approval` independently operable. `action.proposal/v1` is always shadow-only and cannot authorize execution. A non-shadow approval requires the exact independent `action.execution.promotion/v1`; Policy Approval owns the accepted input contract and strict decoder, while Control Plane Host is its only permitted wire producer. Any unknown policy, caller, scope, authorization, promotion, signer, runtime revision, Release BOM, or contract version fails closed. Production activation and promotion issuance are R3 and require human approval and an exact signed Release BOM.

Production composition must use `PostgresPolicyApprovalService.CreateProduction` with separate evaluation, promotion, and revocation P-256 ECDSA public keys; pairwise-identical normalized public-key fingerprints are rejected. It also requires the exact expected least-privilege runtime PostgreSQL role name, a runtime credential that has no superuser/create-role/create-database/replication/bypass-RLS attributes, and a separately held migrator credential. Evaluation, promotion, and revocation private signing keys remain outside this module. Every opened runtime connection rechecks `current_user` and those role attributes. `PolicyApprovalAuthoritativeClient` returns an immutable snapshot whose constructor is internal; the composition root maps it to operation-compiler's `IAuthoritativeApprovalReader` and must preserve the exact decision, canonical digest, and `ACTIVE`/`REVOKED` status without caller overrides.

The runtime-state insert trigger and evaluation transaction acquire the same PostgreSQL advisory lock string for an exact Soul/device/account scope. The trusted state read reuses that already verified connection and the same transaction; it must not open a second pool connection while the scope lock is held. Approved decisions append one rate-consumption fact in the same transaction; parallel proposals on a one-unit budget therefore yield at most one approval. Do not write policy runtime revisions outside the module migration schema because that would bypass this serialization contract.

Downstream dispatch must use the full `PostgresPolicyApprovalExecutionFence` composition with distinct fence-authorization, executor-submission (intent and acknowledgement), independent-reconciliation, and human-recovery P-256 authorities plus a separately protected policy submission-state signer. All five normalized public-key identities must remain pairwise distinct from each other and from evaluation, promotion, and revocation authorities. The policy state private key is injected at the production composition boundary, is never stored in Git or PostgreSQL, and may sign only `approval.submission.state/v1` receipts.

The public composition surface is role-specific. `PolicyApprovalExecutionFenceClient` accepts only `PostgresPolicyApprovalSubmissionExecutorOptions`; its lease publicly exposes revalidation and the no-callback `SubmitNativeOnceAsync` hard stop. Segmented begin, acknowledgement and quarantine are internal/test-only. Executor connection strings must explicitly set `Pooling=false`. Reconciler and recovery retain their separate read/transition clients. All clients and `PostgresPolicyApprovalService` must bind the same pairwise-distinct eight-authority topology.

The current role-specific factories still receive the policy submission-state PKCS#8 private key in process. That is not the final production secret boundary: an independently authenticated state-receipt signer broker/HSM capability must replace raw-key injection and validate the exact caller role, transition, predecessor, evidence, and Release BOM context. Until that broker and its restart/denial tests exist, `releaseEligible` remains false even though PostgreSQL credentials and public transition APIs are split.

The database boundary also requires four pairwise-distinct login roles: the generic policy runtime, submission executor, independent reconciler, and human recovery approver. Executor receives only begin/ack/quarantine; reconciler only reconcile; recovery only recover; the generic runtime receives no lifecycle RPC. None may own objects, inherit another role, mutate lifecycle tables directly, execute validation helpers, or retain an unknown function overload. Keep the three submission credentials in their corresponding trusted processes; injecting all credentials into one untrusted host defeats the persistence-layer separation and is forbidden.

The fence acquires transaction advisory locks for runtime scope, approval, command and attempt in that order. Internal/test-only segmented lifecycle methods exercise durable PENDING, acknowledgement, quarantine, reconciliation, recovery, and crash behavior without granting production native authority. There is no combined native callback path in 0.6.0.

The former Boolean abort callback is not a supported runtime path. It is retained only in historical changelog text; current public composition exposes no native callback. A future owner-defined path must atomically consume one exact signed challenge into ACK or UNKNOWN and must retain/fail-fast on any uncertain termination. ACK/UNKNOWN commit uncertainty may never attempt a competing terminal branch.

The v1 session-lock lifecycle still requires real PostgreSQL verification for recovery compatibility. There is no process-root guardian and no active atomic v2 challenge-consumption migration, so `releaseEligible` remains false. Shared mutable static registries and in-process caller-selected trust are forbidden.

Restart recovery reads the signed append-only state. `SUBMISSION_PENDING` and `UNKNOWN_SUBMISSION` block acquire, revalidation, and pre-submit. `SUBMISSION_ACKNOWLEDGED` and `RECONCILED_SUBMITTED` are terminal. A new attempt is legal only after an independent `CONFIRMED_NOT_SUBMITTED` reconciliation and a distinct human recovery signature bind the next attempt ID, lease ID, attempt number, Release BOM generation, authorization digest, and native-request binding. Recovery never mutates or reopens the old attempt.

For attempt 2 or 3, the executor does not trust recovery table columns alone. Under the already-held scope/approval/command/attempt locks it strictly deserializes the stored prior intent, reconciliation, recovery, and both transition states; verifies executor, reconciliation, recovery, and policy-state signatures; recomputes every stored digest; verifies the predecessor chain; and compares the exact fresh attempt/lease/BOM/authorization/native binding before acquire can succeed. A forged privileged row therefore fails closed before a native-submission lease is returned.

Operation-compiler v1 still reads status during compilation, so compilation alone is not a production-safe revocation guarantee. The execution fence plus durable lifecycle is the required later dispatch boundary. This module remains `releaseEligible: false` until Executor Gateway is rebound to these policy-owned contracts, the real PostgreSQL crash/restart suite passes, and the signed Release BOM records the exact compatible policy/executor versions.

Every ordinary connection and command is bounded to five seconds; the dispatch fence uses a stricter two-second lease. A timeout, missing runtime revision, expired/revoked state, expired promotion, unknown policy, stale status revision, digest mismatch, scope mismatch, inactive kill switch proof, or unavailable database fails closed. Rollback activates `kill_policy_approval`, stops new evaluations and fences, retains immutable receipts, and restores the previous signed BOM; it never rewrites an existing decision.
