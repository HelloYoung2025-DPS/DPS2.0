# Platform Account Registry operations

The module is proposed. Production authorization is disabled until `platform-authorization-authority` verifies raw platform proof and its independently operated external signer can sign `platform.account.authorization.evidence/v1` with the private counterpart of the compiled P-256 root, with the exact authority/account artifact pair represented in a human-approved signed Release BOM. No private authorization key exists in this repository. The kill switch stops authorization writes and new reservation transitions while preserving committed account revisions, evidence hashes/documents, receipts, reservations, and outbox rows. A retained outbox row is replayed with its original payload and idempotency key; unknown or conflicting requests fail closed.

Every initial authorization uses a predetermined canonical `pa_<32 lowercase hex>` ID. The signed envelope binds that ID plus Soul, device binding, platform, alias digest/key ID/key epoch, target status, authorization revision, command trace/idempotency/timestamp, issuer key, Release BOM hash/generation, and a validity window no longer than 15 minutes. Production accepts only the fixed issuer and key ID. Operators cannot substitute a caller-generated public key or downgrade to an opaque approval string.

A held binding reservation uses database time and a five-minute lease. Confirmation freezes the exact authorization revision until binding explicitly releases it. Authorization refresh, suspension, and revocation acquire the same account lock and fail closed while a held-unexpired or active reservation exists. Operators must investigate active reservations that have no matching binding attempt rather than editing provider rows directly.

Rollback restores the previous signed BOM without reversing committed authorization history. It does not pretend an external platform authorization was reversed; revocation must be verified separately. PostgreSQL migrations remain expand-only until the compatibility window closes.

Startup applies embedded migrations under a module advisory lock, verifies the immutable source SHA-256 ledger, then records the active Release BOM and monotonic generation before enabling any read, write, or reservation operation. An edited migration, lower generation, same-generation BOM conflict, or operation attempted before successful initialization fails closed. Evidence is checked again immediately before transaction commit; expiration while waiting on a database lock or fault window rolls back every mutation row.
