# Platform Authorization Authority operations

The module is proposed and `releaseEligible: false`. It intentionally exposes no public production-composition factory. A future separately reviewed trusted host must be added inside this module (or as an explicitly attested friend assembly) before production composition exists. That host may bind only one explicitly trusted raw-proof verifier, a trusted active Release BOM/generation source, an injected durable exact-envelope receipt store, and an external P-256 signature provider whose public SPKI matches the compiled root pin. The issue request cannot select or replace any of those dependencies and cannot report its own BOM or generation.

Raw platform proof is untrusted, bounded to 64 KiB, copied only for the verification call, hashed for idempotency, and zeroed by the issuer after the call. Verifiers must not log or retain proof bytes, credentials, email, phone, login identifiers, cookies, bearer tokens, or raw platform account identifiers. A successful parser call is not authorization; the verifier must return the exact DPS scope, alias digest/key metadata, status, revision, proof digest, and a validity window no longer than fifteen minutes.

The external provider receives only canonical contract bytes and returns an exact 64-byte IEEE P1363 P-256 signature. The module checks the provider identity, key ID, P-256 SPKI, fixed SHA-256 pin, exact compiled SPKI bytes, and the returned signature. No production private key, seed, PKCS#8 value, or test key belongs in configuration, environment variables, this repository, logs, evidence, or the DPS process.

The durable store must serialize `soul_id + device_binding_id + platform_account_id + idempotency_key`, persist the exact canonical signed envelope before returning it, replay the stored bytes unchanged for the same payload digest, and atomically quarantine a different payload digest. The payload digest binds the active Release BOM, generation, runtime trust epoch, and runtime-context SHA-256, so rotating any trusted runtime component makes an old receipt ineligible for replay even if the BOM and generation strings were incorrectly reused. A process-local dictionary is test-only. The repository currently has no production store implementation, so absence of that implementation is a hard release blocker rather than `NOT_APPLICABLE` evidence.

Rollout order is synthetic proof verification, shadow issuance with no account mutation, then a bounded explicitly authorized account cohort. Enable `platform_authorization_authority_v1` only through a human-approved signed BOM. `kill_platform_authorization_issuance` stops new issuance; it must not delete, alter, or resign prior receipts. Rollback restores the previous signed BOM and retains exact receipts so retries remain byte-identical.

Current local locked restores fail closed with `CSSM_ModuleLoad` and package-audit connectivity errors. Direct compiler and test-runner diagnostics do not upgrade the evidence level. A release requires the Manifest commands themselves to return `PASS`, followed by real durable-store and external-signer integration evidence.
