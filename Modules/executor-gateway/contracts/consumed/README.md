# Consumed contracts

- `command.dispatch/v1`, owned by `command-orchestrator`.
- `execution.authorization/v1`, owned by `command-orchestrator`; its canonical domain, digest, algorithm, and signature format are fixed and unknown variants fail closed.
- `approval.execution.fence/v1`, owned by `policy-approval`; a trusted constructor-bound adapter acquires its exact request and short-lived lease, which the gateway revalidates immediately before the durable PENDING transition.
- `approval.submission.intent/v1`, `approval.submission.acknowledgement/v1`, and `approval.submission.state/v1`, owned by `policy-approval`; they are the only public submission lifecycle. Executor Gateway does not publish a parallel pending/acknowledged contract.
- `command.receipt/v1`, owned by `command-orchestrator`; Executor Gateway emits compliant receipts without owning the protocol.
- `command.receipt.signed/v1`, owned by `command-orchestrator`; Executor Gateway signs the exact receipt, command, authorization, active BOM, and evidence binding with its P-256 receipt authority.

The signed authorization's `release_bom_sha256`, generation, and execution-token digest are not accepted as activation truth. An injected verified reader must cryptographically authenticate the supervisor-issued opaque token, enforce monotonic generation anti-rollback, and return current truth for the exact `device_binding_id`. Gateway passes the raw token only to native transport, then rereads generation after native execution and before any successful receipt.

The provider owns Policy Approval credentials and maps the exact command/authorization to `approval.execution.fence.request/v1`; the per-call execution API cannot override proposal, status/runtime revision, runtime-state digest, fence authorization, lifecycle state, or Release BOM scope. Before native submission, its authoritative Begin operation must exact-read policy truth and durably append `SUBMISSION_PENDING`. The native request binds the returned submission-attempt ID, intent digest, and pending-state digest. After a durable native acknowledgement, its authoritative Acknowledge operation must append `SUBMISSION_ACKNOWLEDGED`; only then may the gateway release the fence.

The production adapter must cryptographically verify every Policy Approval lifecycle signature and canonical digest before returning the `VerifiedSubmission*` wrappers. It must also compare `FenceRequestSha256` with the digest of its own fixed request and compare `ProposalSha256` with authoritative policy read-back. It may invoke the callback only when Policy Approval reports `Disposition=Inserted` and `MaySubmit=true`; exact existing PENDING or historical UNKNOWN read-back invokes no callback, no native dispatch, and no retry. Its durable Begin must establish an owner-coordinated cross-commit revocation guard that remains held through acknowledgement or process-rooted guardian transfer. A fresh read alone leaves a TOCTOU window and is insufficient.

Executor Gateway consumes one combined guarded-submission adapter and owns no v1 stop-proof decision path. Any uncertainty after PENDING stays PENDING, is transferred to the process-rooted guardian, and returns only non-retryable `UNKNOWN_OUTCOME/WAITING_EXTERNAL`. Existing PENDING and historical UNKNOWN are blocking states; neither can reach `SubmitFirstByteAsync`. `native.stop.proof/v1` is deprecated quarantine input and cannot authorize UNKNOWN, unlock, retry, or success. Provider failure after possible PENDING or failed guardian transfer invokes host fail-stop and cannot be converted into a signed receipt. No production PostgreSQL, Windows worker, host fail-stop, guardian, or cross-module composition has been verified, so this module remains proposed and release-ineligible. A future confirmed-not-submitted recovery belongs to a new Policy-owned authority contract, a new lease, and the next bounded attempt; Executor does not invent it.
